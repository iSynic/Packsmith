# Unarchiver foundation assessment

**Current direction: Windows first.** This report preserves the original simultaneous three-platform comparison and its run receipts. The [Windows follow-up](windows-first.md) supersedes its Windows XAD build status: a native worker/bundle and the tested preservation subset now pass, with two isolated compatibility patches. The [revised roadmap](implementation-roadmap.md) defers macOS/Linux qualification and retains the required Windows safety, creation/editing and legacy-preservation gates.

The recommended development foundation is a **new native C++ Qt 6 Widgets application with isolated archive workers**. Reuse XADMaster for legacy extraction and maintained engines for creation and editing. Keep the historical Unarchiver fork unchanged as a compatibility reference. PeaZip is the strongest existing-application alternative and deserves a bounded desktop comparison if reducing initial UI work becomes the priority.

**No candidate qualifies for production release under the mandatory gates.** This report completes the local assessment and identifies the experiments needed to close the remaining gates. It does not approve shipping the recommended architecture or claim that the entire requested correctness suite passed.

Assessment selection began September 30, 2026; runs continued into October 1 UTC. Exact commits, releases, asset digests and selection types are in the [source lock](../evidence/sources.lock.json). The fork baseline is `28a2330b16139f6d074cdf75ea34eee0ccd218c4`. All 11 baseline/reference checkouts are clean in the [integrity receipt](../evidence/reference-integrity.json). Experiments and source builds use separate copies or out-of-tree build directories. No donor codec, application source, production UI, repository workflow or published release was changed.

## Failures and their interpretation

1. **Raw overwrite extraction is unacceptable for the product.** Both tested CLIs retain only one of two same-name entries. Windows case-insensitive destinations also collapse case variants. Reject this invocation policy for production. A selected entry needs a stable identity distinct from its display name; collision decisions must happen before writing. This result does not prove that an application with its own entry/output policy cannot use these engines safely.
2. **Stable XAD 1.10.8 does not satisfy the tested legacy encryption case.** A correct 12-character StuffIt password produces file failures; incorrect passwords leave an empty data file and sidecar in the direct-output probe. Head handles both tested password lengths and cleans wrong-password output. Head is unreleased and must earn broader regression acceptance; neither version is a validated legacy release candidate here.
3. **Windows bsdtar CLI is not a validated production extraction/creation path in this build.** ZIP/7z names are unreadable or skipped; TAR names can be mojibake; creation over the Unicode tree crashes with `0xC0000005`. ASCII creation succeeds. The native libarchive probe initializes locale and reads UTF-8 metadata/payloads. Root cause is bounded to this build/path behavior, not established as a universal libarchive defect. The next experiment must compare a fresh MSVC build, explicit wide paths and API-owned file I/O. Do not ship this bsdtar path while unresolved.
4. **7-Zip's tested fallback coverage has limits.** Header-3 LhA is unreadable; the CAB LZX fixture reports a data error despite matching libarchive's upstream payload oracle. Route supported LhA through the qualified legacy backend; expose an unsupported-format/error result when no qualified backend succeeds. This does not imply all CAB or LhA archives fail.
5. **A successful error code alone was insufficient in the initial XAD probe.** Skip-on-collision behavior could report success with zero extracted items. The corrected fresh-destination experiment uses explicit overwrite behavior and checks nonempty payload output. Default enclosing-directory behavior also changes selected output layout. The worker protocol must describe actual outputs and per-entry errors, rather than equating `unarchive` return with completion.

Probe setup corrections included locale initialization, whole-library XAD linking and explicitly loading an installed font for Qt offscreen capture. These are probe corrections, not donor patches. The final Windows screenshot is readable; it remains a synthetic offscreen table, not a finished or accessibility-tested application.

## Performance measurements

These are single-run observations from an existing host, not controlled comparative benchmarks. WSL runs read archives from `/mnt/c`; the final Linux listing overlapped other assessment work. Output formatting differs: XAD emits its richer `lsar -j` output, the native probes emit one JSON line per entry, and 7z emits text. Include output and parser costs when interpreting the numbers.

| 100k-entry listing | Windows elapsed / sampled peak RSS | WSL elapsed / sampled peak RSS |
|---|---|---|
| 7-Zip | 0.433 s / 28.52 MiB | 1.470 s / 24.31 MiB |
| libzip probe | 0.527 s / 36.79 MiB | 0.568 s / 35.75 MiB |
| libarchive probe | 0.302 s / 22.57 MiB | 0.618 s / 22.25 MiB |
| Stable XAD lsar JSON | unavailable | 58.175 s / 256.74 MiB |

The slow XAD listing supports keeping routine mainstream listings on maintained mainstream engines. It does not identify a parser bottleneck independently of Objective-C objects, JSON output, filesystem and WSL effects.

The >4 GiB ZIP64 payload integrity runs take 3.400/3.754/3.626 seconds on Windows for 7z/libzip/libarchive and 3.225/3.124/1.871 seconds under WSL. These are repeated zero bytes, not an incompressible-memory or full-disk benchmark.

The final Qt model has 100,000 virtual rows. Windows offscreen Qt 6.10.2 records 50 heartbeat ticks, maximum gap 16 ms and helper termination after 5 ms; Linux offscreen Qt 6.4.2 records 50 ticks, maximum gap 11 ms and termination after 2 ms. Measurements cover approximately half a second and process termination, not cooperative archive cleanup. ## Application design findings

PeaZip's `peazip-sources/readme.txt` documents Lazarus projects, metadarkstyle registration, optional Win32 drag/drop DLL, GTK/Qt widget sets and separate engine binary packaging. The source separates some listing/utility functions but large `peach.pas` form methods still orchestrate command generation and global UI state. It includes thread/task types, collision/password dialogs and native resources. Some 7z command paths use `pipepw` and a bare `-p`; others concatenate the password option into command text. Display-string password removal is not proof that every process argument is secret-free. No claim is made that the shipped default always leaks passwords. Fresh-desktop keyboard/screen-reader tests, large list insertion, fork display, duplicate identity and recovery need runtime inspection.

Ark's `kerfuffle/archiveinterface.h` and `jobs.h` are useful separations; the libzip plugin supplies progress/cancel and close/discard behavior. `plugins/cli7zplugin/cliplugin.cpp` declares password-bearing argument templates, and the CLI interface uses process/PTY orchestration. Its substantial KF6 dependency set includes KIO, Parts, DBusAddons, FileMetaData and WindowSystem. Such dependencies are legitimate but increase the all-platform packaging surface relative to the small Qt probe. Kerfuffle interface/job files are BSD-2-Clause while the 7z plugin is GPL-2.0-or-later; assess per-file terms before copying. Source inspection does not validate Ark's extraction/update recovery on the target platforms.

For a new shell, library APIs provide stable entry indexes, typed progress/error callbacks and direct password passing. Running those libraries in helpers contains decoder crashes and separates Objective-C/runtime dependencies from the GUI. Stock helper CLIs are quicker to prototype but have text parsing, prompt localization, argument and cancellation limitations. The tested stdin password path makes CLI prototyping feasible; the production interface still needs a versioned structured protocol and SDK/API integration where entry identity, progress or safe output mapping requires it.

## Release gates and next experiments

| Gate | Current state | Required next experiment |
|---|---|---|
| Safe extraction and no data loss | Raw forced overwrite policy demonstrably fails; bounded containment passes. | Per-entry output mapping, duplicate/case/device-name policy and handle-based destination containment; native reparse-point/link race corpus. | All-platform engine/native GUI builds | Windows C libraries/Qt and WSL engines/probes work; Windows XAD and macOS are unverified. | Fresh Windows Objective-C/Foundation worker build; macOS arm64 and x86_64 native XAD/Qt builds. Inspect installed dependencies and run without developer PATH. |
| Faithful legacy preservation | Small Linux sidecar payloads work; stable StuffIt defect and incomplete variant corpus. | Independent StuffIt/StuffIt X, realistic Compact Pro, Amiga LZX and legacy encoding fixtures; native macOS fork/Finder/quarantine oracle; same payloads through Windows/Linux sidecars. |
| Mainstream editing and recovery | ZIP/7z mutations work; one libzip cancellation preserves original. | Replacement-file transaction tested during write, verify, commit and recovery; 7z kill, ENOSPC, destination permissions and original-modification races. |

The highest-value next experiment is the native Windows XAD worker with generated MacBinary/BinHex/AppleDouble hash checks. It is the first shared blocker for every serious foundation. In parallel on a real Mac, run the same fixtures with native resource forks and quarantine checks. If XAD cannot meet either platform gate within a bounded build effort, revisit the architecture before implementing the full GUI; there is no demonstrated replacement for the complete required legacy preservation scope.
